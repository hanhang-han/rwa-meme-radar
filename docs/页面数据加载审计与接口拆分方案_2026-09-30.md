# CliperX 页面数据加载审计与接口拆分方案

**审查时间：** 2026-09-30；对线上公开接口多次读取，并核对当前前后端代码。样本响应时间受公网波动影响，不代表长期 P95。本文记录现状、已确定的直接原因和分步优化方案。

## 现在为什么慢

上线前，除开发者中心外，进入任意页面都会请求 `/api/dashboard?view=overview`、`/api/dashboard?view=market` 和 SSE；SSE 的首次连接还要等 `market` 结果及 JSON 解析结束。首页虽可先拿到轻量概览，但主题图和异动组件又人为等 `snapshotScope` 不是 `overview`，因此主要内容仍等完整市场包。这两个等待已在本轮前端发布中修复。**剩余主要问题**是 Meme、股票和池子列表仍在浏览器分页/筛选，服务器首次仍发送全市场记录。详见 `web/src/main.js`、`web/src/stores/dashboard.js`、`web/src/composables/useStream.js`、`web/src/views/LiveView.vue`。

| 线上接口 | 原始 JSON | gzip 传输 | 记录及用途 |
| --- | ---: | ---: | --- |
| `dashboard?view=overview` | 约 184 KB | 约 26 KB | 12 条热门 Meme、少量股票/关系及完整的汇总/主题信息。 |
| `dashboard?view=market` | 约 4.85 MB | 约 500 KB | 约 1,608 条 Meme、2,988 条股票代币、368 条关系；当前所有市场页都自动请求。 |
| `dashboard?view=full` | 约 11.8 MB | 约 837 KB | API 存在，但正常页面首屏不请求，不能把它当成本次页面慢的原因。 |
| `/feed` | — | 约 15 KB | 至多 100 条成交与 30 条关系，用于实时活动。 |

`market` 原始 JSON 中股票代币约 2.60 MB、Meme 约 1.61 MB、关系约 0.49 MB。一次生产服务器本机 `/api/dashboard?view=market` 读取约 0.14 秒；公网同接口多次约 2.7–9 秒，下载/网络传输是当次主要差距，前端随后还需解析并合并近 5,000 行。不能据此断言服务端永远没有性能瓶颈：后台投影仍定期重建四种快照，负载增大时会争 CPU 与数据库资源。静态 JS 单文件最大约 73 KB，当前首屏主要包袱是数据而非前端代码。API 已启用 gzip 与 ETag，简单再加压缩无法替代减少返回范围。

逐字段统计显示，大头首先是**记录数**，不只是某一个多余字段：股票代币 2,988 行约 2.60 MB，Meme 1,608 行约 1.61 MB；每页实际只显示几十行。股票行中的 `fieldTimes`、`premium`、`issuerIdentity` 合计约 0.75 MB，Meme 行中的 `fieldTimes`、`totalLiquidityCoverage` 合计约 0.36 MB；关系行还有比较和配对证据。这些字段有一部分被页面用于来源、时效、身份或价差，不宜全局直接删掉。应在列表接口返回当前页需要的摘要，将完整身份、价差计算依据、配对证据放在现有详情或按需接口，并保留缺失值与真实零值的区别。

一次全新无缓存浏览器访问首页的网络记录中，概览响应约在导航后 **4.5 秒**、完整市场约 **4.9 秒**，SSE 响应头约 **7.8 秒** 才到，`/feed` 还出现两次请求。此为单次端到端观察，包含静态文件加载、公网网络和当时服务器状态，用于证明请求顺序及重复请求，不当作稳定耗时指标。

## 有多少接口、首屏实际用了哪些

当前 Python API OpenAPI 定义 **25 条路径、26 个方法**。其中 **21 个 GET**，与网站页面数据直接有关的 GET 约 **11 个**：`dashboard`、`stream`、`feed`、`events`、`pair`、`registry`、`token`、`comparisons`、`candles`、`ai/briefing`、`ai/insight`；其余主要是健康、开发者以及对外 v1 API。`overview`、`market`、`full` 是同一个 `/dashboard` 接口的三个视图，不是三条独立路径。不能用接口总数判断快慢，关键是每次页面打开实际取了什么、取多少。

所有普通页面至少请求概览、全量市场、SSE；首页另外读简报和首份 `/feed`；详情页按需读代币、K 线、对比或解读；状态页另读健康。SSE 的 feed 失效事件或断线重置仍可能再次请求 `/feed`，属于数据恢复而非首连固定请求。上线前，配对列表还无用地请求首条配对的代币详情；每个 `RegistryBadge` 会重复取同一 `/registry`；图表即使当前市场的 K 线推送正常也每 31 秒再取 500 根 K 线。本轮已修复这些额外请求；没有当前市场 K 线推送的图表仍保持 31 秒校准。SSE 正常时全市场仍约每 5 分钟校准一次，断流时约每 20 秒整包重取。这些请求的实际次数受连接与组件数量影响。

## 本轮已发布的低风险项

- SSE 用已存在的概览快照游标先连接，不等待完整市场包；完整目录继续后台加载，保持旧列表与详情语义。
- 首页已有的服务端主题图和重要变化随概览先显示；名称线索等必须看全目录的内容仍等待完整数据，避免把部分列表误当全量。
- 去掉配对列表的无用首条详情请求，合并重复的 `/registry` 请求；健康推送时降低图表全量轮询频率，断流时保留校准。
- 去掉 SSE 首连时对 `/feed` 的无条件重复加载；从详情返回全局成交、feed 失效或断线重置时仍按需补数。

这一步改善实时连接和页面可见速度，也减少额外请求；**它不会把 4.85 MB 的 `market` 包消除**。若要根本缩小列表首开数据量，必须同步改变 API、页面分页和 SSE 对列表的更新方式。

2026-09-30 发布到 `/dashboard/` 后，用全新浏览器打开 Meme 页复核：概览请求约在导航后 1.34 秒发起，完整市场和 SSE 均在约 1.68 秒发起，SSE 约 1.84 秒收到响应；完整市场约 6.04 秒收到响应头、12.35 秒完成下载，浏览器测得传输约 498 KB、解压后约 4.86 MB。此单次样本证实 **SSE 不再等待完整市场包**，也说明列表慢仍由整包传输主导。首页首连只请求一次 `/feed`，并能在全量市场完成前显示主题图。公网时延有波动，不能把这一组耗时当作长期指标。

## 建议的接口拆分

按页面用途增加接口，而不是把同一大 JSON 机械切成多个仍全部请求的小包：

| 用途 | 建议接口 | 首次返回 |
| --- | --- | --- |
| 首页 | 复用现有 `GET /api/dashboard?view=overview` | 汇总、主题图、重要变化、热门股票/Meme、少量新成交与线索；返回 `asOf`/`cursor`。现有概览已较小，不必为了多一条路径而新建 `/home`。 |
| Meme 列表 | `GET /api/memes?chain=&sort=&cursor=&limit=50` | 当前页记录、总数或下一页游标；保留价格时间、来源与缺失状态。 |
| 股票列表 | `GET /api/stocks?chain=&sort=&cursor=&limit=50` | 当前页股票及所需关系摘要；详情证据另取。 |
| 池子列表 | `GET /api/pairs?chain=&sort=&cursor=&limit=50` | 当前页已核验关系和最小行情摘要。 |
| 全局搜索 | `GET /api/search?q=&limit=20` | ID/名称/合约及跳转信息，不要求浏览器持有完整目录。 |

现有 `/api/token`、`/api/candles`、`/api/comparisons`、`/api/events`、`/api/health/data` 可继续服务详情与专页。后台投影应按首页、Meme、股票、池子分开构造或增量更新；只新增端点、仍在每次请求里重建全量快照，会把瓶颈从网络转回服务器。SSE 保留全局游标，新增事件按用户当前页的链/资产/交易池更新可见行；排序变化或断线过久时按页重取。前端搜索和分页逻辑迁到服务器后，才停止自动请求全量 `market`。新接口应逐页设置返回字段，首屏尽量只取 50 行及必要的来源、时间和状态；完整价差依据、发行方证据和池子明细留给详情接口。旧 `market` 接口先保留兼容，待页面迁移验证后再调整调用方。

## 验收目标

首页应在不请求全量市场包的条件下完成主要内容和 SSE 连接；Meme/股票/池子第一页只下载该页记录；详情页只读目标资产与当前 K 线。为新接口制定实际压缩包大小、首屏时间、慢网络下可用时间，并验证来源/时间/真实零值/缺失值、排序分页不重不漏、SSE 更新和重连游标一致。数字目标须在实现和压测后确定，不把一次公网耗时当保证值。
